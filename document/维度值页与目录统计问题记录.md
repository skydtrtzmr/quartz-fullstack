# 维度值页与目录统计问题记录

记录日期：2026-10-15。

本文记录本轮已确认的问题、已做修复及待讨论的架构调整。按目录静态生成维度值页目前只是建议，尚未确定或实施；不以本文作为继续改代码、回退或重建现有业务域的授权。

## 一、当前设计及原始目的

- 为减少生成页面数量，同一个字段、取值在业务域内共用维度值页，例如 `_dimensions/项目经理编码/未分类`。
- 通过运行时 `scope` 参数限定目录，通过 `context` 限定关联来源，通过 `filter` 追加祖先分类条件。
- 构建期生成共享维度 HTML、维度 JSON 和字段/取值 manifest；浏览器根据参数生成最终计数、列表和图谱视图。
- 多个主体共用一个维度定义是合理需求，但它不必意味着多个目录共用同一个 HTML 页面。

## 二、已确认的问题及当前修复状态

| 问题 | 原因 | 当前代码中的修复 | 验证范围 |
| --- | --- | --- | --- |
| 目录维度入口显示 10，维度预览显示 11 | 维度产物将 `project/` 目录页也算为未分类实体，目录入口则排除了目录页 | 在维度插件中共用源实体判定，排除目录索引页、系统页和虚拟占位页 | 单测和独立演示域产物验证 |
| 增量构建后目录总数、维度入口保留旧值 | 增量影响分析关注链接、标签，未显式表达目录页对后代文件的依赖；有实体 `index.md` 的目录页可能被跳过 | 核心补所属目录和祖先目录依赖；SQLite 构建重新解析受影响的目录源文件，避免目录正文被缓存中的元数据替代 | 真实新增、分类修改、跨目录移动、删除，以及目录正文保留验证 |
| 预览数量未反映目录范围 | 原预览移除查询参数，并直接复制静态 HTML，不执行维度运行时筛选 | 核心预览保留参数并区分缓存，通过通用 `popover-created` 事件，由维度插件显示筛选后的数量和列表 | 浏览器验证：全域未分类 3 个，项目范围预览为 2 个；另有 scope/context/filter 回归测试 |
| 跨目录分类值可能链接到错误页面 | 目录入口在局部值域内分配 slug，而共享页面在全域值域内消解冲突，例如 `A B`、`A-B` | 目录入口复用全域维度计划中的字段、取值 slug；构建内缓存并复用该计划 | 跨目录 slug 冲突测试 |
| 子目录采用不同规则时，父目录维度可能多算 | 父目录入口按自己的规则统计全部后代，而维度页根据实体所属上下文决定字段是否生效 | 目录入口复用维度值索引，按各实体实际生效的规则计数 | 嵌套目录不同规则测试 |
| 分类最后一个成员消失后，旧页面仍可访问 | manifest 更新，但旧维度 HTML、JSON 未删除；空计划也可能提前返回 | 维度 emitter 按旧、新 manifest 差异删除失效产物，空计划写出空 manifest | 单测及独立演示域真实增量验证 |

注意：目录增量依赖遗漏是独立的构建问题。即使改为静态维度值页，这项修复仍然需要保留。

## 三、不是同一统计口径的数量

- 文件夹底部的“此文件夹下有 N 条笔记”目前沿用 folder-page 的当前层条目数量，子文件夹算一个条目，不是全部后代笔记总数。
- 文件夹维度入口统计当前目录子树内的实体，因此包含子目录中的实体，排除目录页自身。
- 共享维度页未带筛选参数时统计全域；带参数进入后显示对应筛选范围。
- 因此，修复失效刷新和目录页多算后，并不是所有位置的数字都应相等。是否调整底部文案或统一为子树实体数量，尚未确定。

## 四、当前修复的架构边界及待收敛点

### 可以独立保留的修复

- 由核心构建层维护目录页的增量依赖，并保留受影响源页的正文。
- 在维度插件内统一实体判定、字段取值和 slug 映射，减少各入口之间的口径差异。
- 构建过程复用全域计划，避免每个目录重复扫描、计算同一份维度域。

### 需要重新评估的实现

1. **动态预览复杂度。** 为了显示正确数量，引入预览生命周期事件、目标 URL 参数解析、异步 JSON 加载和按参数区分缓存。它能工作，但增加了维护成本。若目录范围静态化，应评估是否可移除这些专项动态初始化逻辑。
2. **生成页面清理职责。** 当前维度 emitter 同时清理维度 HTML 和 JSON；JSON 属于 emitter，HTML 属于页面分发器。长期更适合由核心统一管理生成页面的生命周期，避免插件分别维护 HTML 删除规则。
3. **同一套筛选语义有多个使用者。** 维度列表、图谱和预览都需正确处理 scope/context/filter。当前专项测试通过不等于所有组合、所有导航路径都已覆盖。

上述事项属于设计取舍和维护性风险，不能仅凭“测试通过”认定架构已足够简洁；也不能把所有修复笼统认定为 hack。

## 五、待评估方案：目录范围静态化，临时筛选动态化

建议评估以下方向，暂不实施：

- 为实际存在的“目录 × 生效字段 × 实际取值”生成独立页面。
- 在构建期确定该目录范围的数量、基础列表和基础图谱数据，使普通预览可以直接展示静态内容。
- 共享字段定义、规则及组件，不强制共享同一个 HTML 页面。
- `context` 关联来源、祖先条件组合等临时筛选继续动态处理，不为全部排列组合生成静态页。
- 图谱节点按需展开与页面是否静态化是两个维度，不应因静态出页而回退为浏览器一次性计算全部图谱关系。

### 决策前需要确认

1. 目录范围是否包含整个子树，哪些目录实际需要生成维度页。
2. 是否保留全域共享维度入口；保留时与目录维度页如何区分。
3. 实际页面数、JSON 体积、构建耗时和增量影响范围，尤其是 20,000 文件业务域。
4. 能否复用数据，避免按目录出页后重复保存大量节点和边。
5. 新旧 URL、书签及图谱跳转入口的兼容方案。
6. 页面静态化后，哪些预览事件和运行时过滤代码可以删除，哪些仍为临时筛选所必需。
